# Database Design

The platform uses one **central spreadsheet** for tenants, users, settings and the audit log.
Gym business data (members, payments, …) will live in **one spreadsheet per gym**, referenced
by `Gyms.Spreadsheet_ID`, in a later phase.

The schema is defined once in `backend/apps-script/src/Config.gs` (`SCHEMA`). Running
`initializeDatabase()` creates the tabs and headers from it.

## Conventions

| Rule | Detail |
| ---- | ------ |
| IDs | `<PREFIX>-<32 hex chars>` from `Utilities.getUuid()`, e.g. `GYM-3f2b9c0d…`. Generated by the backend, immutable, never reused. |
| Prefixes | `GYM` Gyms · `USR` Users · `SET` Gym_Settings · `LOG` Platform_Audit_Log |
| Timestamps | ISO-8601 UTC strings (`2026-11-24T10:15:30.000Z`), set by the backend |
| Cell format | Every column is plain text (`@`), so Sheets never converts IDs, dates or numbers |
| Enums | Upper-case values, validated on every write |
| Formula safety | Values starting with `= + - @` are written with a leading `'` so they stay text |
| Header row | Row 1, frozen. Column order is significant: do not reorder or rename columns |
| Deletion | Rows are never deleted by the API. Deactivate with `Status` instead |

## Per-gym spreadsheets (Phase 4)

Every gym has its **own spreadsheet**, referenced by `Gyms.Spreadsheet_ID` and created by
`initializeGymDatabases()` or provisioning. Reasons: physical separation of each gym's data,
and the 10-million-cell limit per spreadsheet.

- The spreadsheet ID comes only from the central `Gyms` row. It is never accepted from a
  client and is returned only to platform admins (gym users see `dataStoreReady: true|false`).
- **Defence in depth:** every per-gym table also stores `Gym_ID`, and every read and write
  filters on it. Even if two gyms were misconfigured to share a spreadsheet, neither could see
  the other's rows. `validateDatabase()` reports shared spreadsheets, and setup refuses them.
- The same data layer (`SpreadsheetService.gs`) serves both kinds of spreadsheet through a
  "db handle"; the central schema is `SCHEMA`, the per-gym schema is `GYM_SCHEMA`.

### Members.Trainer_ID (Phase 9)

A trailing column added to the per-gym `Members` tab: the `User_ID` of the member's trainer
(an active `TRAINER` of the same gym) or empty. `initializeGymDatabases()` appends new
trailing columns to existing tabs automatically — only when the existing headers are an exact
prefix of the new ones; anything else still stops with an error and nothing is written.

## Concurrency

All writes run inside `LockService.getScriptLock()`. The web app executes as one account, so
this single lock serializes writes from every user. Inside the lock, rows are re-read before
they are updated, so a stale row number is never used. "Find, then create or update" sequences
(setting upsert, unique Firebase_UID) happen inside one lock, so concurrent requests cannot
create duplicates. If the lock is not acquired within 10 s, the request fails with
`503 LOCK_TIMEOUT` and can be retried.

## Scaling notes

Each request reads the `Users` tab, plus `Gyms` when needed. That is fine for thousands of
rows. Revisit (per-request caching or an index) if the tabs grow past roughly 10–20k rows.
Google Sheets limits a spreadsheet to 10 million cells.

## Editing data by hand

- Use the provisioning function or the API where possible. For manual edits, keep the
  `<PREFIX>-<32 hex>` ID format and ISO timestamps, and never edit IDs.
- Deactivate rather than delete. Deleting a gym row locks its users out
  (`GYM_NOT_FOUND`); deleting a user row returns `USER_NOT_REGISTERED`.
- Run `validateDatabase()` after manual edits.
